## Context

T01 focus: "Actions based on what the graph shows". The prep context fixes the boundary: "Target the team's own demo repo. Never post to real Kubernetes repos." MCP's specification says hosts must obtain explicit user consent before invoking tools with side effects (https://modelcontextprotocol.io/specification/latest). v1 of this ADR used its own staleness heuristic (latest milestone two releases behind, and similar), which disagreed with `03` tool 26; v2 derives drafts from the audit's verified findings so the action follows directly from what the graph shows.

## Decision

- The only action is **drafting an issue that reports a verified inconsistency in a KEP's records**. A draft can be made only from an open `Finding` in `kep` (ADR 0024) of kind `stage_mismatch`, `milestone_mismatch`, `one_sided_replacement` or `status_label_conflict`. Findings of kind `declared_approver_never_approved` are shown in the audit but never become drafts, because an issue would single out a person.
- Two steps, two surfaces: `draft_stale_doc_issue(finding_key)` (Q&A agent and HTTP; not MCP, B17) returns a proposal composed only from the finding's evidence rows (each item as `label/key → url`); the api's action service persists it as an `ActionDraft {finding_key, …}` through `kb_ops` (ADR 0022). Posting requires `POST /v1/actions/stale-doc-issue/{id}/confirm` from the web dialog by a human, who may edit title, body and labels; the dialog shows the target repository verbatim from configuration and offers no picker; the confirm carries a server-issued nonce and performs a compare-and-set on `ActionDraft.status`.
- Target repository `ACTION_REPO` (`owner/name`, default name `kep-brain-demo-actions`). The confirm handler refuses unless the owner is in `ACTION_REPO_OWNER_ALLOWLIST` **and** not in the built-in denylist `kubernetes`, `kubernetes-sigs`, `kubernetes-client`, `kubernetes-csi`, `cncf` (case-insensitive). `ACTIONS_ENABLED=false` by default; caps `ACTIONS_DAILY_CAP=10`, `ACTION_CONFIRM_LIMIT=3/h` per IP (B18).
- The posting token is a separate fine-grained PAT on the bot account with `issues: write` on that one repository; the ingestion tokens cannot write anywhere.
- Every posted issue body starts with a fixed line stating it was generated by KEP Brain during Graph Hacks from public data, lists the evidence links and names the request id; `ActionDraft.external_url` is stored and the finding gets a `FindingNote {kind: drafted}`.

## Alternatives considered

- A separate staleness heuristic (v1): a second definition of "wrong" next to the audit's; two answers to one question.
- Posting directly after a confidence threshold: irreversible; the confirm click is itself the "graph proposes, human decides" moment.
- Other actions (assign reviewers, label issues): out of scope and NodeOps's territory.
- Dry-run only: the T01 bullet asks for an action with an effect; a controlled demo repository satisfies it.

## Consequences

- Integration tests: a denylisted owner is refused even with a misconfigured allowlist; 20 parallel confirms yield one issue; a draft from a `declared_approver_never_approved` finding is refused.
- The README's T01 section shows a posted issue in the demo repository with its evidence block and the finding it came from.

## Revision 2026-10-12

Drafts now come only from verified findings (aligned with `03` tool 26); person-naming findings excluded; persistence through `kb_ops`; nonce and compare-and-set adopted from B13/B18 (design review R4, R5, R7, R13).
